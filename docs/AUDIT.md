# Engineering Audit Log

This is the **technical** companion to `CHANGELOG.md`. `CHANGELOG.md` stays terse and user-facing, following Keep a Changelog conventions — this file is where the actual engineering detail behind each release lives: what was found, what was verified against the real code (not guessed), what broke and why, and what's still open. Each entry maps to one or more `CHANGELOG.md` versions but goes deep where the changelog stays shallow.

Format: one dated section per audit pass, newest first. Each item states what was done, how it was verified, and — where relevant — what's still outstanding.

---

## 2026-10-07 — pending-embeddings queue for notes (#231)

A note was embedded once, fire-and-forget, at the moment it was saved, with nothing remembering a failure: if the app was killed or the embedder was not ready (`embed` answers `[]`), the note never got a vector. Now `EmbedAndStoreNoteUseCase` writes a row to a new `PendingEmbedding` Isar table and `NoteEmbeddingWorker` drains it one note at a time (vector stored first, row deleted last; app-start nudge; retry after 5 min when the embedder is not ready; a row is dropped after 3 throws). Layout and rules in `docs/SHIVA/rag.md`.

- **Benchmark (new `integration_test/embedding_benchmark_test.dart`, profile build, vivo 1933 / Snapdragon 710, 4 notes)**: one at a time 46.3 s, 2 at a time 46.2 s, `generateEmbeddings` in 4s 46.2 s, all at once 46.2 s — **about 11.5 s per note and 1.00x for every method**. The same figure in debug and profile builds. The log shows the CPU (XNNPACK) delegate although the GPU backend was requested. This contradicts the 20–80 ms in the old scheduling doc (corrected) and the premise of #125. The embedder returned 768-dim vectors where the app declares 1024 (already #234).
- **Before and after on the phone (`integration_test/note_save_timing_e2e_test.dart`, same test on `main` and on this branch, vivo 1933)**: one note stored after 12.1 s before, 11.8 s after (unchanged: the embed is the same). A burst of 4 notes saved at once: before, all four vectors appeared together at ~46.5 s; after, one at a time at 12.4, 24.1, 36.1 and 47.8 s (newest first), so the first note is searchable about 4x sooner and the last lands about 1 s later. A Shiv question arriving right after a burst of 4: answered after 57.9 s before, 23.1 s after. The worker does not make embedding faster; it stops the question waiting behind the backlog and makes the first notes usable sooner.
- **Chat while an embed runs (`integration_test/chat_embed_contention_e2e_test.dart`, Gemma 4 E2B + Gecko)**: a chat turn alone took 1.58 and 1.60 s to the first token and 7.9 and 8.8 s for the whole reply; started while a note embed was in flight, 1.65 s and 9.6 s, and the embed itself took 12.2 s instead of ~11.5 s. So a running embed costs a chat reply roughly 10-20 % and the first token almost nothing, on this phone where the model runs on the GPU and the embedder on the CPU. Two alone samples and one contended, one phone, one short reply: indicative, not a benchmark. The worker's stand-down while chat is generating means at most the one embed already in flight overlaps a reply.
- **Verified**: real-Isar tests for the repository; worker tests for ordering (newest first), vector-before-row-delete, not-ready keeps rows, retry timer (fake clock), no overlapping embeds under many nudges, a note queued at the moment the table looked empty, drop after 3 failures; entry use case tests. Breaking the "go again" flag, the delete-last ordering and the attempt limit each turned a test red (the first needed a dedicated race test). Device test `note_embedding_queue_e2e_test.dart` (queue → embed → similarity hit → row gone).
- **Worker and chat**: the worker stands down while a Shiv chat reply is being generated (`InferenceScheduler.isChatRunning`, checked before each note, polled every 2 s); other jobs (Gana, extraction, Nataraj) do not hold it back. It has no timer except a 5-minute retry after a failed pass, and no database watcher, so idle it costs nothing. **Not covered**: notes saved before this table that never got a vector, and a store format bump (#232) — both need a cheap per-note "has a vector" check, which this PR does not add; re-embedding every saved note would take about 11.5 s each on this phone. 
- **Shared gate (added in the same change)**: `EmbeddingQueue` now has one slot and two priorities and sits inside `EmbeddingService.embed`, so a question never waits behind queued notes or PDF/DOCX chunks (it waits only for the one embed already running, up to ~11.5 s on the vivo 1933) and the note worker and the document indexer take turns. The queue was 2-wide before; the benchmark shows 2 at a time is no faster. `EmbedAndStoreChunkUseCase` no longer wraps its own queue call (it would have deadlocked on one slot). Verified by queue and service unit tests, the integration test, and a device test that checks order, not time.
- **Bug found by the integration test**: `EmbeddingService.embed` answers `[]` for a model that is not loaded *and* for a text it failed on; the worker treated both as "not ready", so one failing note at the front would never be counted or dropped and would block the queue for good. The worker now keeps and stops only when `isReady` is false, and counts a loaded embedder's empty answer as that note's failure.
- **Speed**: nothing here makes embedding faster; the benchmark found no gain from batching or from 2-at-a-time. The gains are not losing notes and not making a question wait behind a backlog. Measured on the vivo 1933: a 4-character text took 11.54 s, ~200 chars 11.53 s, ~1,500 chars 11.57 s, ~6,000 chars 11.61 s. The cost does not depend on the text at all: the plugin's forward pass is compiled for a fixed input (it rejects any batch other than 1, `pooling.dart`, and the model name says 1024 tokens), so every call processes a full padded input. That is why batching and 2-at-a-time gain nothing. The levers left are a model with a shorter fixed input (it would cut the cost, by how much is not measured) and getting the GPU backend to load on this phone (it falls back to the CPU; not investigated).
- **Extraction untouched**, by decision: skipped when no model is active, drained only away from Shiv so chat keeps priority.

## 2026-10-06 — Gana dashboard (#87)

A Dashboard page that replaces the old Gana list (same route `shivGanaList`; one screen with New button, back button, totals, per-Gana cards and activity) plus lifetime counts on the detail page. The run log keeps only the last 10 runs per Gana, so totals could not come from it: `GanaModel` gains `runsSucceeded` / `runsFailed` / `runsSkipped`, bumped by `writeGanaRun` in the run-log transaction (both isolates already write through it). Page layout and the meaning of the numbers are in `docs/SHIVA/Ganas.md` §10.

- **Counters are nullable on purpose**: Isar reads a missing field on an old row as the minimum integer, not 0, so a non-nullable counter would start at about −9e18 on existing installs. Existing Ganas start at zero, so totals only count runs from this version on (the page says so).
- **`upsertGana` replaces the row**, so without preserving the counters every edit or toggle would have reset them; it now copies them from the existing row (test: an edit keeps them).
- **Verified**: real-Isar tests for counting (each status, running not counted, re-written runId counted once, unknown Gana, pruning keeps totals) and for edit-preserves-counters; widget tests for the dashboard page (totals, attention list, rows, activity, switch), its navigation (New, a Gana, the empty state), the detail page (stats, run list, note lookup, fallback), the stat tile and the outcome bar; sabotage checks (dropping the once-per-run guard, the counter copy, the activity limit, the attention filter, the bar's row stretch each turned a test red). On a phone (`integration_test/gana_dashboard_e2e_test.dart`, seeded rows removed afterwards): numbers, attention list and outcome bars render. The first screenshot showed no bars — the segments collapsed to zero height; fixed and covered by a test.
- **Not verified**: dark theme and Hindi on a device; a real engine run updating the page live (the page uses the same Gana-table watcher as the list, and counters live on that row, but no live run was observed); whether a counter write racing an edit in another isolate can lose a count (same race the cursor already has, not guarded).
- **Run detail (detail page)**: each run in Recent runs is a drop-down. A succeeded run opens to the note it published (looked up by `outputEventId` through `ResolveNotesByIdsUseCase`, so it also works for group messages and DMs; an Open note button for feed and group notes), a failed run to a plain-words title and hint plus the raw error in a selectable box, a skipped run to a sentence per `GanaSkipReason` instead of the enum name. Errors are sorted into no identity / publish / network / model / other by `GanaRunError.parse`, **a best-effort reading of the raw message text** (the log stores only the text), so an unrecognised message lands in "Something went wrong" with its raw detail still shown. Verified: unit tests for the parser (kinds, wrappers, unicode, empty, 20k chars), widget tests for the tile, sabotage checks, and on a phone (`gana_dashboard_e2e_test.dart`) the published note text and the opened list render.
- **Not verified**: the failed and skipped tiles on a device (the screenshot cut off below the first run); a note evicted by retention on a device (only the widget test covers the "no longer on this device" text); the dashboard's recent-activity list still shows only a status line per run, not this detail.
- **Not built**: per-run duration (the log does not store it), charts over time.

## 2026-10-06 — device tests run from a pre-set model

Device integration tests no longer download an AI model each run. `flutter test` uninstalls the app, which wiped the model; now it is pushed once to `/data/local/tmp/uniun_test/` (the uninstall does not touch it) and `provisionTestModel(AIModelId.…)` (`integration_test/support/test_model.dart`) copies it into the app folder, registers it and marks it active. Default model Gemma 4 E2B. Runs use `--no-uninstall` so the copy survives; `scripts/device_test.sh` wraps the push, keeping the screen on/unlocked, and the run. Usage is in `test/TESTING.md`.

- **Verified on a phone (Gemma 4 E2B)**: `gana_local_engine_e2e_test`, `flutter_gemma_bg_isolate_test` (needed the copy into the app folder — the worker isolate cannot restore a model registered from outside it), `scheduler_preemption_test` (three runs, ~2.2–2.4 s), `scheduler_model_switch_test` (passed; its second test skips with one model).
- **Found by running them for real**: the two scheduler tests had never run (they skip without a model) and failed on their own bugs — mixed `maxTokens` made flutter_gemma rebuild the model (33.5 s), a fixed 500 ms wait during a cold load, a 5-minute re-queued essay, the preempted run logged as finished first, and a 1.5 s budget from a much smaller model (now 4 s). App code unchanged; see #260.
- **Not verified**: the whole `all_tests.dart` suite in one go; the "test starting" screen was never looked at (only that it does not break the run); `scheduler_model_switch_test` failed once in ~2 s straight after another test and passed on the next run, cause not found; its second test needs two models; the cloud device tests still need an API key.
- **Not done from #88**: more device tests (only the model ones were moved over), and a CI-style runner.

## 2026-10-05 — image input in Shiv chat (first slice) — work in progress

A Shiv chat message can carry one photo when the active model reads images. Which models: `AIModelId.supportsImages` (the Gemma 4 pair only — Qwen3 0.6B and DeepSeek R1 have no vision encoder, per flutter_gemma 1.8.3's model table), carried to the UI as `LlmModelInfo.supportsImages`; cloud models report false until the gateway takes images.

- **UI**: an attach button in `ShivInputComposer`, present only for a vision model (`ChatImageSupportCubit` re-reads the active model on open and after the model sheet closes); gallery pick downscaled to 1024 px by `image_picker`; a thumbnail with a remove button; sent with the next message, then cleared. A photo is dropped, not sent, if the model changed to a text-only one after it was attached, and a photo with no text does not send.
- **Engine**: vision is fixed when the engine is created (`getActiveModel(supportImage, maxNumImages)`), so the first image turn asks flutter_gemma for a vision model, which rebuilds a cached text-only engine itself (seconds, once); the vision model is then kept for text turns until the model changes. Image turns use `createChat` — a `.litertlm` engine rejects images on `openChat`'s concurrent sessions (found on a device, not by the unit tests). Text turns are unchanged: `openChat`, `supportImage` unset.
- **Verified**: unit/widget tests at every layer (flag, cubit, composer, bloc, use case, repository, data source, runner) with the plugin behind its gateway fake; each of ten deliberate breaks turned a test red (the one that slipped, the data source dropping images, got a test).
- **Verified on a phone**: `integration_test/chat_image_turn_test.dart` on Gemma 4 E2B — a solid-red image is answered "Red", and a text turn after it works.
- **Not verified**: Gemma 4 E4B; prefill time and memory with a real photo; whether the engine re-create on the first image turn is acceptable (not timed).
- **Not built**: the photo is not shown in the sent bubble or stored in the conversation (it lives for the turn); camera capture; more than one image; how image tokens count against the prompt budget (RAG context is added as for any turn).

## Open items carried into v3.0.0

The detailed entries up to v3.0.0 were cleared when it shipped; they remain in git history
(`git log -p -- docs/AUDIT.md`). These are the things from them that were not resolved:

- **Android GPU crash on one device class.** On a vivo 1933 / Android 11 / Adreno phone, creating the GPU engine intermittently kills the process inside the vendor GPU driver (`SIGSEGV` in `libgsl.so`). Shipped deliberately with GPU preferred; no fix upstream yet.
- **Note search likely has the same limit document search had.** Notes still use ToStore's approximate index, which reached only 24 % of stored vectors once it held ~80. Documents moved to an exact scan; notes did not.
- **The graph is untested on a device after the Obsidian rewrite** (simulation timing, drag and tap feel). Its performance test is `integration_test/graph_simulation_perf_test.dart`.
- **iOS is unverified** for everything in this release (it cannot be built from the Linux dev machine): document viewing, ML Kit OCR and labeling, the graph, and the GPU/engine bump.
- **Hindi/Hinglish retrieval on real scans is still weak** (the English-centred embedder and noisy Devanagari OCR); the keyword-side fix is in, the rest needs a better embedder or OCR.
- **`InferenceScheduler`'s T2 soft budget can stall an extract-only queue** (latent, predates 3.0). `maxOutputTokens` is unused, so a runaway one-shot generation runs until the KV cache fills.
- The OCR and chart-reading thresholds in `page_ocr_plan.dart` (50 %, 25 %, 20 characters, the Word picture sizes) are unmeasured on real documents.

## How to keep this file useful

- Add an entry here for anything with real technical weight behind it: a root-caused bug, a dependency decision with a rejected alternative, a verification gap that's real and worth knowing about, a discovery that contradicts existing docs.
- Don't duplicate `CHANGELOG.md` — if there's nothing more to say than what the changelog already says, it doesn't need an entry here.
- Be honest about what wasn't verified, not just what was — a gap flagged here is more useful than a claim that turns out to be wrong later.
